## 二、反思题（PRD 第十四章）

### 1. 为什么 V2 下单导入链路不能继续采用同步阻塞方式？什么时候同步反而更简单可靠？

同步阻塞下，10,000 行文件的解析、校验、写入都在单次 HTTP 请求内完成：Vercel Serverless 有执行时长上限（超时即整个任务丢失），多用户并发大文件会打满数据库连接池（逐行查询/插入），且失败无法定位、无法重试、用户无进度感知。异步事件驱动把"上传"与"处理"解耦：上传只建任务返回 task_id，处理由队列+Worker 异步消费，可并发、可重试、可恢复、可追踪。同步反而更简单的场景：文件极小（百行内）、无并发、单机部署、失败可整体重来、无需进度——此时引入队列的复杂度大于收益。

### 2. 处理单元变大或变小，会分别带来什么影响？

变大（如 4,000 行/批）：批次数量减少、调度与进度更新开销降低、批量 SQL 单次吞吐更高，但单批内任一行失败的重试范围翻倍、单条 SQL 参数过多在网络高延迟下传输变慢、内存峰值升高。变小（如 500 行/批）：重试粒度更细、单批执行更快、进度更新更平滑，但批次数翻倍带来更多调度/往返开销。本项目实测从 1,000 行/批调到 2,000 行/批后，批次从 11 降到 6、固定往返成本减半，全链路从 61.8s 降到 53.5s（本地直连）。

### 3. 吞吐从 10,000 提升到 50,000 单/分钟，最先成为瓶颈的是哪个？如何扩展？

按成本递增：数据库写入（UPSERT 的 I/O 与索引维护）通常是最终硬瓶颈；其次 Worker 消费能力（CPU/解析）；Redis 队列一般先扩容节点即可。扩展路径：① 先横向加 Worker 实例（2→6），但需同步控制数据库连接池；② 若数据库写入是瓶颈，改批量 UPSERT→COPY/临时表合并、加分区、优化索引、必要时读写分离；③ Redis 用集群或提高吞吐（批量 pipeline）；④ 容量推导必须按最慢环节核算，否则加再多的 Worker 也只是把压力推到数据库。

### 4. 队列消息重复投递，为什么"业务幂等"比"消息只投递一次"更重要？

分布式系统无法保证"恰好一次"（at-most-once 会丢消息，at-least-once 必然可能重复）。若依赖"只投递一次"，一旦网络抖动/消费者处理成功后确认丢失，消息重投就会造成重复入库或进度重复累计。业务幂等（稳定业务键 + 状态机门闩）让重复投递变得无害：同一 task_id+row_index 的 UPSERT 覆盖写、批次 processing→completed 只成功一次，重复消费直接返回。本项目用 `@@unique([taskId, rowIndex])` + 批次状态门闩实现，压测验证重复消费不重复写入、不重复累计进度。

### 5. 处理单元中部分行失败，应整体回滚还是成功行先入库？为什么？

成功行先入库。批量导入的业务语义是一行电话错误不应让整批 10,000 行全部失败：失败行写入 `import_task_errors`（行号/字段/错误码/脱敏值），成功行正常 UPSERT，任务终态标记 `partial_success`，用户在错误明细页可逐行定位修复后重导。整体回滚只适用于强一致事务（如金融对账）——导入场景的"部分成功+可修复"更符合业务价值，这也是 PRD 状态规则明确支持的。

### 6. 错误明细保留原始值但手机号/地址是敏感信息，如何平衡排障效率与数据安全？

落库前脱敏：`masking.ts` 对 receiverPhone/Name/Address 分别做 `138****5678`、`张*`、保留前 6 字打码，`import_task_errors.raw_value` 存脱敏值；查询接口返回的已是脱敏数据。排障仍能定位到"行号+字段+错误码+脱敏值+错误原因"，足够判断问题类型；确需原始值排查时走管理端权限+审计，假设说明中已声明脱敏策略。

### 7. Outbox 表增长到千万级，如何清理、归档和设计索引？

索引：`(status, next_retry_at)` 已建，投递查询只走该索引；`created_at` 排序用于 FIFO。清理：已 `sent` 且超过保留期（如 7 天）的事件按 `created_at` 分批 DELETE（每批小事务，避免锁长表）；`failed` 死信单独归档到冷表/对象存储后再清理；保留期与归档策略在运维文档中可配。千万级时可按 `created_at` 分区（按月），或改为"已 sent 事件仅保留最近 N 条 + 明细走日志/对象存储"。

### 8. AI 规则导致大量字段映射错误，监控如何区分是规则问题还是数据库问题？

监控看板的**错误类型分布**是关键：规则映射问题通常表现为 `E006 规则映射失败` / `E002 必填缺失` 集中爆发且跨任务稳定复现；数据库问题则表现为 `E007 写入失败` 或阶段耗时（validate/insert）的 P95/P99 异常抬升 + 5xx 增多。通过 Trace 检索按 task_id 展开时间线，可看到是"解析/映射阶段"还是"写入阶段"失败；按 error_code 筛选错误明细，若错误集中在特定字段（如全部 skuCode 错位）基本可判定为规则问题。本系统 E001-E008 错误码 + 阶段耗时分布 + Trace 组合即可快速归因。
