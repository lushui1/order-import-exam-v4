# 《重构假设说明》（PRD 模块十一 · 强制）

本文档回答 PRD 要求的 12 项设计决策，是架构评审与压测报告的依据。

---

## 1. 为什么选择异步事件驱动，而不是继续同步处理

V2 现状是「上传 → 解析 → 校验 → 批量写库」在单次 HTTP 请求内同步完成。10,000 行文件下：

- 解析 + 规则引擎 + 校验 + 写入全程阻塞请求，Vercel Serverless 函数超时（默认 10s，可配置上限有限）；
- 多用户并发大文件时数据库连接池瞬间打满（逐行 SKU 查询 + 逐行 INSERT 是主要消耗）；
- 用户无进度感知，失败无法定位到行；
- 无法重试：请求超时后整个任务丢失。

改为异步事件驱动后：
- 上传接口只做「存文件 + 建任务 + 写 Outbox」，1 秒内返回 task_id；
- 文件解析、校验、写入由队列 + Worker 异步消费，可并发、可重试、可恢复；
- 每个批次独立处理，部分失败不影响成功行；
- 全链路 trace_id 贯穿，故障可定位到批次与行。

同步方案仅在文件极小（百行内）、无并发、无重试诉求时更简单可靠，不适用于大促批量导入场景。

## 2. 处理单元大小如何设计，为什么这样设计

采用 **2,000 行/批**（`BATCH_SIZE = 2000`）：

- 解析：Excel 10,000 行解析耗时主要在首次，批次间通过内存缓存共享解析结果（`parseCache` 缓存 Promise，并发批次共享同一次解析），避免每批重复解析；
- 校验：2,000 行去重后 SKU 批量 IN 查询一次完成（≤ 2,000 个 SKU，单次查询毫秒级）；
- 写入：2,000 行单次原生 SQL 批量 UPSERT（ON CONFLICT (task_id, row_index)），一次事务提交；
- 重试成本：单批失败重试范围小，幂等键保证重复消费不重复写入；
- 与 60 秒目标匹配：10,000 行 = 6 批（2,000 行/批），并发 6 一轮完成，实测全链路 53.5s；
- 初始设计为 1,000 行/批（11 批），实测 61.8s 略超目标；调整为 2,000 行/批后批次减半、固定往返成本减半，实测 53.5s 达标。

选择 2,000 而非更大（4,000）：批次过大会放大单批重试成本与单次 SQL 参数规模（Neon 网络延迟下超长 SQL 传输慢）；2,000 行是批量性能与重试粒度的平衡点，且 PRD 4.1 明确允许 500/1000/2000。

## 3. Worker / Consumer 的容量规划

- Worker：常驻 Node 进程（`scripts/worker.ts`），BullMQ `concurrency = 2`；
- 压测直连脚本：并发 6（= 批次数，一轮完成），规避高网络延迟下的轮次等待；
- 部署建议 2~4 个 Worker 实例（Railway/Render/Fly.io 常驻进程，Vercel 仅承载 API），每实例并发 2；
- 队列：BullMQ + Redis（本地或 Upstash），Job `attempts: 5` + 指数退避（2s 起）。

容量推导（10,000 行，本机→Neon 实测）：
```
批次: 6 × 2,000 行
消费并发: 6（一轮完成）
每批实测: 14~45s（含约 8~10 次串行 DB 往返 × 单次往返 ~4s 网络延迟）
全链路实测: 53.5s ≤ 60s
```
同区域部署（Vercel + Neon 同 us-east-1）下网络往返降至毫秒级，耗时将大幅下降，60 秒目标有充足余量；实际以压测报告数据为准。

## 4. 10,000 单/分钟的性能推导

| 阶段 | 操作 | 次数 | 单次估算 |
|---|---|---|---|
| 文件解析 | 规则引擎解析整文件 | 1 次（批次共享 Promise 缓存） | ≤ 2s |
| 规则执行 | 字段映射/聚合 | 含在解析内 | - |
| SKU 校验 | 6 批 × 1 次批量 IN | 6 次 | ~1.6s/批 |
| 批量写入 | 6 批 × 1 次批量 UPSERT | 6 次 | ~6.2s/批 |
| 进度/日志 | 每批 1 次更新 + 1 次聚合查询 | 6 次 | ~0.2s |

实测总耗时 53.5s（含本机→Neon 网络延迟），目标 ≤ 60s。数据库峰值连接 = 消费并发 6 × 每批事务连接数（Prisma 连接池复用），远低于连接池上限。

## 5. 数据库连接池和 Worker 并发如何控制

- Worker 并发固定 2（BullMQ `concurrency`），避免多 Worker × 多并发打满连接池；
- 所有查询走 Prisma 连接池（默认 `pool_size`，可按环境调优）；
- SKU 校验与写入均为批量操作（每批 1 次查询 + 1 次事务），杜绝逐行 I/O；
- 监控看板展示队列积压，积压超过 5,000 行橙色预警，指导扩容决策。

## 6. Outbox 如何避免"任务创建成功但消息丢失"

- 任务、批次、Outbox 事件在**同一数据库事务**内创建（`createImportTask` 内 `$transaction`）；
- Dispatcher 轮询 `event_outbox` 中 `pending/failed` 且 `next_retry_at <= NOW()` 的事件，`SELECT ... FOR UPDATE SKIP LOCKED` 防并发重复领取；
- 投递成功标记 `sent + sent_at`；失败累加 `retry_count` 并按指数退避（1/5/30/120/600 秒）重试；超过 5 次标记 `failed` 并写告警 Trace；
- 服务宕机恢复后，未 `sent` 的事件仍在表中，Dispatcher 重启即继续投递；
- 禁止"只在接口里直接 queue.add 而无本地记录"——所有事件先落 Outbox，再投递。

## 7. 处理单元 Job 如何做到幂等

- **稳定业务键**：`orders` 表 `@@unique([taskId, rowIndex])`，UPSERT 基于该键（等价于 external_order_no + sku_code + line_no）；
- **批次状态机**：`pending → processing → completed`，Worker 通过 `UPDATE ... WHERE status='pending'` 原子抢占，仅抢占者执行；
- 已完成批次再次消费直接返回（幂等快速路径）；
- 进度累计仅在 `processing → completed` 的原子更新内 `increment`，重复消费不重复累计 `processed_rows/success_rows/failed_rows`；
- 单元测试验证 `classifyRows` 纯函数无副作用（重复输入结果一致）。

## 8. 部分行失败时为什么允许成功行继续入库

业务场景是批量下单：一行电话错误不应让整批 10,000 行全部失败。设计为：

- 失败行写入 `import_task_errors`（含行号/字段/错误码/脱敏原始值）；
- 成功行正常批量 UPSERT；
- 任务终态：全部成功 `completed`，部分失败 `partial_success`（PRD 状态规则）。

用户可在错误明细页逐行查看并修复后重新导入（前端错误页支持按批次/错误码筛选、分页）。

## 9. SKU 校验降级的触发条件和风险提示

- 触发条件（PRD 模块十）：SKU 主数据查询超过 3 秒（`SKU_VALIDATE_TIMEOUT_MS = 3000`）或数据库连接短暂失败；
- 降级行为：跳过 SKU 主数据存在性校验（E001），仅保留本地格式校验（必填/电话/数量）；
- 降级不静默：任务记录 `degraded=true + degraded_reason`，写入 Trace 事件（`SkuValidationDegraded` / `ImportTaskDegraded`），监控看板展示降级任务数；
- 前端任务页明确标注「⚠️ SKU 校验已降级：本次导入未经过商品主数据完整校验，数据可能需要后续复核」；
- 服务恢复后新任务自动恢复正常校验（降级判断基于当前查询结果，非全局开关）；
- 降级任务是否补校验：当前版本不自动补跑，需人工复核（可在后续版本实现补校验 Job）。

## 10. 错误日志中敏感数据如何脱敏

`src/lib/masking.ts`：

- 手机号：`13812345678 → 138****5678`；
- 姓名：`张三 → 张*`，`欧阳娜娜 → 欧阳**`；
- 地址：保留前 6 字，其余 `*`；
- `import_task_errors.raw_value` 落库前经 `maskValue()` 脱敏（按字段名分派，仅 phone/name/address 敏感）；
- 错误查询接口返回的 `raw_value` 已是脱敏值，前端无需二次处理。

## 11. 压测数据如何生成、如何清理

生成：`npm run seed:sku`（`scripts/seed-data.ts`）

- 清理旧 SKU（`sku_code LIKE 'SKU_%'`）后重建 20,000 条（SKU_00001~SKU_20000，含名称/规格/单位）；
- 生成 `test-data/10000-orders.xlsx`（10,000 行，SKU 从主数据随机抽取）；
- 故意注入：20 行非法 SKU（E001）、15 行非法电话（E003）、10 行非法数量（E004）、5 行空 SKU（E002）——用于验证错误定位能力；
- 生成配套解析规则 `load-test-rule`。

清理策略（重复执行即可，无脏数据累积）：

- SKU：按前缀 `SKU_` 删除重建；
- Excel：文件覆盖写入；
- 规则：按名称 `load-test-rule` 删除重建；
- 压测产生的任务/批次/错误/性能日志：不自动删除，可定期按 `created_at` 归档或清理（PRD 考点 6 清理策略）。

## 12. 需要向产品/运维确认的问题

1. 相同文件重复上传：当前允许创建新任务（每个任务独立 task_id），是否需要在业务层做文件指纹去重？
2. 降级任务是否需要自动补校验 Job？补跑时机与范围（全量/仅降级行）？
3. 错误明细保留周期与脱敏策略是否需要按合规要求调整（当前手机号/姓名/地址脱敏）？
4. 队列与数据库的可用性告警渠道（钉钉/邮件）由谁负责接入？
5. 生产环境 SKU 主数据规模与增长速率，决定 `sku_master` 是否需要分区/缓存预热；
6. 压测环境的 Worker 实例数与 Redis 规格由运维分配还是自动弹性？
7. 历史 V2 同步链路数据（`orders.import_id` 关联的 Import 记录）是否需要在迁移期保留双写？
8. 监控看板的数据保留时长（当前保留全部历史，是否需要按月归档）？
